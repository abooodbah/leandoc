# ADR 0001: Rendering engine

- **Status:** Accepted
- **Date:** 2026-10-20

## Context

LeanDoc must render `.docx` faithfully enough to trust, on Windows, Linux, and
macOS, without running or fetching anything the document contains. The handoff
named three candidates:

1. **docx-preview** (`docx-preview` 0.4.1, Apache-2.0) inside the system web
   runtime, which LeanMark's hosts already harden.
2. **A native C++ parser emitting HTML**, in the style of LeanMark's MD4C core.
3. **Hybrid:** native unzip, XML parsing, and fidelity analysis; docx-preview
   for layout.

A second JavaScript engine, mammoth.js 1.13.0 (BSD-2-Clause), was measured as
the alternative to docx-preview. Mammoth produces clean semantic HTML but by
design drops page size, margins, headers, footers, fonts, colours, and table
styling, so it cannot provide a page view.

## Spike

Harness: [`docs/spike/spike.mjs`](../spike/spike.mjs), documents generated by
[`docs/spike/make_docs.py`](../spike/make_docs.py). Each engine rendered each
document in a fresh headless Chromium 141 (Playwright 1.64 build 1194) on
Linux, under LeanDoc's intended Content Security Policy, five launches, median
reported. Memory is the proportional set size and private memory of the
Chromium process tree after 1.5 s. Machine: CI-class Linux container, 4 vCPU,
15 GiB RAM.

| Document | Engine | Render | First paint | DOM nodes | JS heap | Tree private |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 3-page report | docx-preview | 96 ms | 114 ms | 162 | 6.8 MiB | 291 MiB |
| 3-page report | mammoth | 106 ms | 124 ms | 90 | 10.0 MiB | 292 MiB |
| 300-page report | docx-preview | 230 ms | 508 ms | 13,064 | 6.5 MiB | 344 MiB |
| 300-page report | mammoth | 307 ms | 444 ms | 6,860 | 4.6 MiB | 369 MiB |
| Arabic letter | docx-preview | 84 ms | 100 ms | 30 | 6.5 MiB | 288 MiB |
| Arabic letter | mammoth | 107 ms | 122 ms | 16 | 9.8 MiB | 293 MiB |

Both engines raised zero CSP violations and made zero requests outside the
page origin. The absolute tree figures are dominated by headless Chromium's
own baseline (about 285 MiB on this machine with an empty page) and say
nothing about WebView2 on Windows. They are fit for comparing the engines with
each other and are not to be quoted as product figures.

Quality observations from screenshots of the same render:

- docx-preview reproduced page size and margins, headers and footers, theme
  heading colours, a merged table cell, run colour and bold, numbered lists,
  and `w:bidi` paragraphs (`direction: rtl`).
- docx-preview did not draw bullets whose glyph is a Symbol-font private-use
  character (U+F0B7), which is how Word writes the default bullet. This is a
  font mapping problem fixable in the reader.
- Mammoth produced no page boundaries, headers, or colours.

A native C++ HTML renderer (option 2) would need to reimplement style
inheritance, numbering, tables, sections, and notes before reaching the
fidelity docx-preview already has. The spike showed parsing is not where the
time or memory goes: the whole 300-page render took 230 ms, and the process
tree cost is the web runtime's, which a native HTML emitter would still pay.

## Decision

LeanDoc uses the **hybrid** design:

- A portable C++17 core (miniz for ZIP, pugixml for XML) owns every
  security-relevant step: bounded reading and inflation, DTD refusal, feature
  analysis for the fidelity report, the outline, and writing a sanitized
  package that contains only allow-listed parts with external references,
  macros, embedded objects, and comments removed and tracked changes accepted.
- The reader lays out only that sanitized package with a pinned copy of
  docx-preview and JSZip, and adds LeanDoc's own fixes (symbol bullets,
  right-to-left checks, link interception).
- Hosts are LeanMark 0.3.0's three thin native hosts, copied and adapted.

## Consequences

- Three platforms from the first release with the packaging LeanMark already
  proved.
- docx-preview's layout limits become LeanDoc's: no line-level pagination
  (pages break at explicit and last-rendered page breaks), and no text boxes,
  equations, charts, or SmartArt in 0.1. The fidelity bar discloses each.
- The reader never sees the original bytes, so a docx-preview parsing bug
  cannot reach a remote template, macro, or external image, and the CSP is a
  second barrier rather than the only one.
- Two copies of document parsing exist (core analysis and docx-preview
  layout). The core does not try to predict layout; it only counts and strips.
- docx-preview and JSZip updates are deliberate: pinned in `package-lock.json`,
  listed in `THIRD_PARTY_NOTICES.md`, re-tested against the fixture set.
